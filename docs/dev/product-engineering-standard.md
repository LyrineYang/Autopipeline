# 产品工程规范：用户入口、扩展接口与内部实现

适用对象：AutoPipeline 及后续同类 Python 库、CLI 和 agent 产品。
资料核对日期：2026-09-15。本文是项目采用的工程约定，不是外部认证标准。

目标是让用户能安装、完成真实任务、理解结果并可靠升级，让扩展作者能接入能力，
让维护者能调整内部实现。干净的界面应减少用户必须理解的概念，同时保留影响
结果、成本和恢复操作的信息。

本文定义后续实现和验收的目标，不表示现有产品已全部达标。
当前用法见 [README](../../README.md)，开发资料见[开发者入口](README.md)。

## 1. 成熟项目提供了哪些可借鉴的做法

| 参考对象 | 官方做法 | 我们采用的原则 |
| --- | --- | --- |
| [SciPy：公共 API](https://docs.scipy.org/doc/scipy/reference/index.html) | 明确列出公共命名空间，区别实现模块，说明不兼容变更的弃用过程 | 可导入不等于受支持；公开入口及其稳定性必须有清单 |
| [scikit-learn：扩展 estimator](https://scikit-learn.org/stable/developers/develop.html) | 第三方组件遵循一致的接口，并用 `check_estimator` 等通用检查验证行为 | 扩展接口是对开发者交付的产品；提供可重复执行的契约检查 |
| [pytest：插件](https://docs.pytest.org/en/stable/how-to/writing_plugins.html)及[兼容政策](https://docs.pytest.org/en/stable/backwards-compatibility.html) | 用明确的 hooks 接入插件；兼容变更考虑用户和插件作者，提供迁移过程 | 扩展通过指定入口调用核心；内部重构不能随意破坏外部集成 |
| [Click：帮助页面](https://click.palletsprojects.com/en/stable/documentation/) | 命令组展示简短说明，子命令提供参数、默认值与案例 | 按用户当前任务逐层提供信息，完整能力仍可发现 |
| [PyPA：源码布局](https://packaging.python.org/en/latest/discussions/src-layout-vs-flat-layout/)与[项目元数据](https://packaging.python.org/en/latest/guides/writing-pyproject-toml/) | 说明源码目录对导入和安装测试的影响，并定义构建、依赖与发布元数据的配置方式 | 以实际安装包作为交付物验收，明确运行依赖和构建要求 |
| [Diátaxis：文档组织](https://diataxis.fr/) | 按学习、完成任务、查询和理解四种需要组织文档 | 文档同时考虑读者和阅读目的，避免把操作步骤与设计讨论混写 |

以下“必须”“应该”“可选”是结合这些资料作出的项目选择，不能归因于所有参考库。
不要求更换为 Click、继承 scikit-learn 的类或复制 pytest 的插件系统。

## 2. 四类边界，以及不同的隔离强度

| 类别 | 服务对象与内容 | 对外承诺 |
| --- | --- | --- |
| 用户入口 | CLI、配置、结果报告、安装与使用指南；有需求时提供 Python SDK | 能完成任务；输入、输出、副作用和兼容范围明确 |
| 公共扩展接口 | 自定义 workload、agent backend、evaluator、benchmark adapter | 文档化的调用协议、错误行为和版本兼容；扩展作者不必理解整个运行时 |
| 内部实现 | 搜索节点、内存、调度、缓存和具体模块布局 | 可重构；不作为外部集成前提，已公开的旧入口须先迁移 |
| benchmark 与维护工具 | 题目、评分、实验统计、研究脚本、发布工具和设计资料 | 独立生命周期；通过公共接口使用产品，不成为普通安装和运行的必要条件 |

开发者有两种角色：扩展作者和产品维护者。面向前者的接口需要稳定承诺，
不能把所有“开发内容”都视为随时可变的内部细节。

隔离按需要逐项建立：

- **信息隔离**：默认帮助与用户文档聚焦任务，高级参考和历史设计有独立入口。
- **接口隔离**：外部调用依赖受支持的协议，核心实现可以变化。
- **依赖与分发隔离**：安装产品无需安装维护工具或拉取 benchmark 数据。
- **执行隔离**：限制生成代码对主机、凭据和文件的访问；需要单独的运行环境设计。

隐藏命令、下划线命名、独立目录和候选文件复制，都不自动提供执行安全隔离。
当前本地执行模式必须说明会运行用户或 agent 提供的代码。

## 3. 规范强度与使用方式

- **必须**：相关能力交付前满足的验收条件；未满足须标为缺口，不能声明已达标。
- **应该**：默认做法；偏离时在同一变更说明中记录具体理由及替代验证。
- **可选**：有实际需求再引入，不作为成熟度的装饰性要求。

新功能和被修改的接口遵守适用条款；历史缺口按影响排序迁移，不要求一次重写。
产品发布按其声明的支持范围验收。缺少 CUDA 资源会阻塞 CUDA 兼容性结论，
不会阻塞 CPU 产品、安装体验、接口或文档的独立改进。
日常变更无需另建方案文档，可直接在 PR 中写清场景、边界和验收证据。

## 4. 实现标准与验收条件

### U1：用户工作流完整，默认界面克制

**必须**为主场景提供从输入到可用结果的一条推荐路径。每条路径说明前提、
执行命令、预期结果、失败后可做什么；不要求用户先理解 planner、搜索节点或日志事件。
默认值、设备要求、网络访问、外部资源、可写范围和付费调用条件应在操作前可见。

**必须**区别运行完成、正确性通过、未找到改进和取得改进。无收益可以是合法结果，
执行失败或未验证不能以“成功优化”呈现。摘要使用延迟、加速比、调用量等用户概念，
调试字段和逐事件记录从详细报告访问。

**应该**采用“主帮助 → 子命令帮助 → 完整参考”的结构。高级参数按实际任务组织；
调试入口保留可发现性。若将来有 GUI，也应调用同一应用逻辑。

**验收**：从干净环境按用户文档完成真实输入的初始化、执行、报告及结果复用；
再检查一个常见失败，用户能据提示继续。不得用合成 smoke 替代这条路径。

### A1：公开接口是明确的兼容契约

**必须**在接口参考中列出受支持的 CLI 命令、配置项、机器输出、环境变量，
以及准备对外支持的 Python 符号和扩展协议。逐项标注稳定、实验性或已弃用。
文档中推荐的用法不得一边被用户采用，一边以“内部实现”名义无提示删除。

**必须**说明输入输出、默认值、错误、副作用、资源所有权和支持版本。
机器可读输出与供人阅读的日志分开；脚本不应依赖报告文案或终端排版。
持久化配置、运行结果和导出清单应各自定义版本及读取规则：
兼容字段可以扩展，无法理解的必需字段或版本要明确拒绝；不能静默猜测。

**应该**将新增公开 Python 入口收敛到产品命名空间，并用显式导出清单表达意图。
内部模块使用清楚的私有命名。是否增加 SDK 由真实嵌入需求决定，不能仅为目录对称
包装一套与 CLI 行为不同的 API。

**验收**：公开用法仅导入声明的入口；兼容测试覆盖仍受支持的旧配置、旧导出物和
关键调用。内部模块移动后，这些用法仍成立或得到已公布的迁移提示。

### A2：核心、扩展与 benchmark 职责清楚

**必须**让核心定义所需协议，由 adapter 把外部能力转换到协议。新增 benchmark
不能要求修改搜索核心中的题目分支；第三方 adapter 不应依赖搜索节点的可变内部状态。
业务规则保持一份实现，CLI、报告入口和兼容脚本调用它。

AutoPipeline 中，sensing 收集证据，profiler 解释执行耗时和硬件行为，
evaluator 运行测量，验证后端决定候选是否正确、是否值得保留。
agent 的自述和 benchmark 的单个 PASS 字符串不能替代验证所需的完整证据。

**必须**让 Level 5 与 apimetric 的题目、基线、评分和实验统计留在独立 benchmark
开发线。adapter 可以随产品交付，但核心不能反向依赖其未发布源码或本地 worktree。

**应该**提供扩展契约检查，覆盖成功、无效证据、超时、异常和资源清理。
**可选**：多个独立扩展确有分发需求时，再引入插件发现和插件版本协商。

**验收**：独立目录中的扩展通过已安装产品完成一次实际评估；修改 adapter 不改变
固定题目的判定语义。benchmark 自身的正确性和评分仍由 benchmark 侧验收。

### P1：交付物独立于开发工作区

**必须**以构建出的 wheel 验收用户路径：新虚拟环境、源码目录之外、没有源码
`PYTHONPATH`，使用交付包及声明的依赖完成工作。不能依赖本机绝对路径、Git 状态、
`workspace/` 内容或 editable install 偶然暴露的文件。

**必须**将运行必需的模板与数据纳入包，排除凭据、缓存、实验产物和独立站点；
保留许可证与来源说明。设计文档保留在源码资料中，不因 wheel 精简而删除。
若提供标准 sdist，须验证从 sdist 构建 wheel；普通 Git 源码归档不得冒充此项验证。

**必须**让 Python 范围、构建后端版本、依赖和平台标记与实际使用的特性一致。
可选能力在被调用时检查依赖，并给出可执行的安装建议；帮助、配置检查等轻量功能
不应因缺少 CUDA 或模型框架而无法启动。

**应该**使用独特的包命名空间，避免占用 `models`、`tree` 等通用顶层名称。
新库优先采用 `src/` 布局；已有项目先建立安装包验收，再迁移目录和旧导入。
库的依赖范围表达兼容约束，复现实验的环境记录固定实际版本，二者分开管理。

**验收**：检查 wheel 文件清单；在隔离环境完成用户流程和缺依赖路径；
对声称支持的依赖下限与主要平台组合有验证。目录美观不能替代安装行为证据。

### O1：失败可理解，执行有边界，结果可复验

**必须**在付费调用或昂贵计算前验证可提前发现的问题：配置、输入、设备、依赖、
输出冲突和基线是否有效。说明调用次数、超时与金额预算各自能约束什么。

**必须**定义取消、超时、子进程失败和部分输出的处理行为：结束所管理的执行、
记录失败原因、保留有效证据，且不把残缺结果标为通过。不覆盖用户原始输入或已有
结果；重新运行是否续跑、能恢复到哪里，必须与实际能力一致。

**必须**保存足以复验的输入和参考标识、候选、配置、版本、测量条件及判定。
外部权重无法打包时记录其来源或获取方法、标识、校验方法与必要权限。
默认诊断内容不泄露凭据；详细日志可定位，性能任务保留 profiler 入口，
无法采集时明确原因。

**验收**：无效输入不触发后续昂贵操作；失败留下可读原因而非成功结果；
导出包在声明的资源条件下能重新评估。取消与超时按实际执行后端分别测试。

### D1：文档按读者与任务组织

**必须**保持唯一的推荐用户入口。README 回答用途、适用场景、安装、第一次成功、
结果含义和主要限制；使用指南承接任务步骤；参考文档提供完整参数和格式。
贡献、扩展和维护资料从开发入口访问，历史设计标注用途并保留。

**应该**按 Diátaxis 的阅读需要区分教程、操作指南、参考和解释，但不强制建四套
目录。高级用户也需要参考，扩展作者也需要入门案例；“用户/开发者”不能代替
对文档目的的判断。一个事实只保留一个主要维护位置，其他页面链接过去。

**必须**说明案例的资源和真实性：随机初始化网络能验证执行流程；本地预训练权重
能验证模型接入；付费 coding agent 能验证真实修改闭环。它们不能互相替代，
也不能自动证明代表性任务上的优化收益。

**验收**：用户不阅读设计文档就能完成主流程；从用户入口能找到完整参考与开发
入口；本地链接有效，命令与当前交付版本一致，无已移出项目的维护步骤。

### R1：版本演进与发布承诺可执行

**必须**在发布前明确支持范围、安装来源、已知限制和回退办法。Alpha 可以保留
实验性接口，但必须明确标记，不能只凭版本号推断稳定性。发布说明区分新能力、
修复、行为变化、弃用和迁移，不把测试数量当成功能成熟度。

本项目对未来标为稳定的接口采用以下政策：**修复版不主动破坏兼容；破坏性删除
安排在主版本，并先跨至少两个已发布次版本提供替代入口、警告和迁移示例。**
实验性接口变更也须在发布说明中给出影响与新用法。必要的紧急例外须解释原因及
恢复路径。此政策是本项目选择，不等同于 Python 的版本格式规范。

**必须**保证发布版本、源码提交、包元数据及验收记录可对应；只测试过源码时不能
宣称发布包已通过验收。正式发布前检查包内许可证、依赖声明和支持矩阵。

**验收**：针对实际交付包执行适用检查；由旧版配置或案例验证迁移；发布说明中的
每项能力都能指向用法或证据。是否公开发布、是否承诺新的收费或资源使用由授权决定。

## 5. 没有 GPU 时，如何继续推进产品

验收按要回答的问题拆分。资源不够时记录缺口、最小资源与替代路径，继续能独立
推进的工作；下面的资源是申请模板，不是未经估算就固定的服务器规格。

| 要验证的结论 | 为什么影响下一步 | 最小资源与用户动作 | 无资源时继续什么 |
| --- | --- | --- | --- |
| 安装包能完成用户工作流 | 决定能否交给别人试用 | CPU 环境和声明的运行依赖；通常工程侧自行准备 | 修复安装、接口、失败处理、报告和导出；不等待 GPU |
| 真实 agent 能修改实现并走完独立评估 | 决定 agent 接入和反馈是否可用 | 配置一个支持的 agent，完成认证并批准一次受限调用预算；不需要下载 coding agent 权重 | 检查协议和进程行为；合成测试只证明控制流程 |
| 自有模型能正确接入 | 决定用户是否能处理实际任务 | 用户提供模型代码、合法可访问的权重位置、输入形状与样本；按模型估算内存 | 用内置模型验证通用执行；保留私有模型接入缺口 |
| 目标 CUDA 栈兼容 | 决定能否支持该部署环境 | 先按 workload 的显存需求选择单张目标 GPU；用户提供登录方式或运行诊断并回传结果 | 准备同一安装包、命令与采集流程；CPU 结果不作为 CUDA 证明 |
| 优化有可重复的收益与合理成本 | 决定算法和默认预算是否值得保留 | 已跑通的目标环境、代表性题目、重复测量时间和 agent 预算；用户决定可接受的成本/延迟取舍 | 固定基线、评分、日志和比较方法；不许诺收益 |

“真实模型”必须在具体任务中说清：是负责写代码的远端 coding agent，还是被优化
的 PyTorch workload。前者通常通过已配置服务调用；后者可能需要本地预训练权重。
两类资源分别申请，不能把“需要模型”一概解释为需要下载大型权重。

资源申请写明：当前问题、会改变的决策、为什么现有资源不足、最小配置、
用户取得资源的步骤、预计耗时/成本及估算依据、预算上限、无法提供时的替代方案。
付费或新增外部访问承诺需要授权；普通技术选择和已有范围内的修复继续自主完成。

## 6. AutoPipeline 如何按此规范落地

本节是 2026-09-15 的迁移起点，基于当前源码检查；不是永久项目状态或已完成承诺。
进度在后续变更和[发布检查](open_source_readiness.md)中更新。

| 优先级 | 当前依据与缺口 | 下一项实现及完成条件 |
| --- | --- | --- |
| P0：安装与发布可信 | CI 已有 wheel 外部目录初始化检查，但实际 CPU 集成测试仍在源码目录运行 | 把 CPU 评估、报告、导出复验加入安装包外部目录验收，阻止源码导入掩盖漏打包 |
| P0：构建声明正确 | `pyproject.toml` 使用字符串许可证及 `license-files`，构建下限却是 `setuptools>=69`；PyPA 对这些新字段列出的 setuptools 支持起点为 77.0.3 | 在构建变更中校正下限并验证隔离构建；本次规范文档未修改构建配置 |
| P1：公开契约 | 已有 CLI 和协议文档；`OptimizationTask` 仍直接使用 `SearchNode`、`RootMemory` 等内部类型 | 先列公开接口与稳定性，再设计最小外部 adapter 契约；用独立扩展验证，不一次公开全部内部类型 |
| P1：分发命名空间 | wheel 仍包含通用顶层包名 `tree`、`pipeline` | 审计导入消费者和冲突，逐步收敛命名空间；旧入口通过兼容层迁移，独立 benchmark 仍可调用 |
| P1：产物兼容 | 验证报告已有 `verification-report/v1`；不能因此推断所有配置、结果与导出都具备升级契约 | 逐类登记 schema 和读写版本，补历史产物的读取与拒绝行为检查 |

## 7. 每次变更的最小交付说明

直接写进 PR 或现有任务说明，不额外创建模板文件：

1. **用户场景与实际变化**：谁给什么输入，操作后得到什么；重要假设是什么。
2. **接口影响**：改变哪一类边界；旧命令、配置、产物或扩展如何继续工作。
3. **验收证据**：执行入口、环境、交付版本和实际结果；说明测试对应哪项承诺。
4. **下一项关键验证**：为什么值得先做，缺什么资源，怎样获取，以及无法获取时推进什么。

验证随变更而定：纯文档检查链接和用法一致性；接口变更验证契约及兼容；
运行与打包变更执行受影响的真实用户路径；性能主张需要目标环境的重复测量。
不以新增文件、参数、测试数量或抽象层数量作为完成标准。
